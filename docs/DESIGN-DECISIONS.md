# 设计融合决策（DESIGN-DECISIONS）

> 背景：本项目存在两版设计。
> **方案 A（玩法驱动）**：真实在售池 + 官方营养即卡面属性 + 确定性随机 + 概率公示 + 保底 + 端盒 + 收藏图鉴 + 抽→下单闭环。
> **方案 B（合规驱动）**：事实层/创意层严格分离 + 情绪映射 + 三档选择模式 + 不自动下单 + 会话内收藏 + 概念视觉强制标注。
>
> 本文档逐条裁决两者的冲突，形成唯一实现基线。**编码以本文档为准**；与 PRD/SPEC 冲突处，以本文档为最新。

---

## 总原则

> **盲盒只负责"制造惊喜"，MCP 只负责"提供事实"，AI 只负责"表达情绪"。三者不得互相冒充。**

这句话直接推出一个工程约束：**不允许任何字段同时承担"事实"和"创意"两种角色**。因此卡片必须物理拆成三层（见 D1），而不是"一个对象里混着官方名和自创文案"。

---

## D1 · 数据结构：三层拆分（采纳 B，并扩展一层）

| 方案 | 做法 | 问题 |
|---|---|---|
| A | 单层 `Card`，`name`/`price` 与 `flavorText`/`rarity` 混在一起 | 下游分不清哪个字段能信、哪个是编的 |
| B | 双层 `MealFact` + `MysteryBoxConfig`/`Result` | 缺"可复现审计"所需的元数据 |

**裁决：三层。**

```text
fact        ← 只能来自 MCP 返回，缺失即 null，禁止补齐
experience  ← 只能来自本项目规则/模板，禁止伪装成官方
meta        ← 种子、指纹、模式、时间、免责声明（用于复现与审计）
```

落地：`draw.py` 输出 `{fact, experience, meta, series}`，任何字段归属错误视为 bug。

**硬规则**：`fact.*` 一旦为 `null`，`experience.*` 不得用推测值填充它（例如无营养数据时不得"按名称估算热量"）。缺失就展示"数据待补"。

---

## D2 · 是否闭环下单：保留，但加"确认门"（A 的差异化 + B 的安全边界）

这是两版最大分歧。B 主张 MVP 不碰下单，A 主张"抽完就能买"是核心价值。

**裁决：两者都对，因为它们说的不是同一件事。**

- B 反对的是：**抽盒动作本身触发副作用**（抽一下就把单下了）。这条必须遵守。
- A 主张的是：**抽完能顺畅进入下单**。这是产品价值，不能砍。

因此定义**两道门**：

```text
门 1（只读门）：抽盒 → 展示 fact 真实价格 → 允许调 calculate-price 算总价（只读）
门 2（写入门）：create-order 必须满足全部条件才可执行：
   ① 用户在抽盒之后，用明确语句表达下单意图（"下单/就要这个/帮我点了"）
   ② 已向用户复述：门店 + 就餐方式 + 商品名 + 数量 + 应付金额（精确到分→元）
   ③ 用户对该复述再次确认（一次确认不算，必须是对复述的确认）
   ④ 抽盒结果未被替换（换了卡要重新走 ②③）
```

**默认行为**：抽盒结束语是"要下单吗？"，而**不是**"已为你下单"。未获确认时，最多做到 `calculate-price`。

> 这条同时满足赛事"真实使用 MCP"（用到了 calculate-price / create-order）与"不诱导消费、不越权操作"。

---

## D3 · 稀有度：保留，但重新定义 + 强制免责

B 的担忧成立：食物没有"限量款"，自称"隐藏款"会让用户误以为是官方发行体系。

**裁决：保留机制，改名 + 改语义 + 加免责。**

| 项 | 旧（A） | 新（基线） |
|---|---|---|
| 名称 | N/R/SR/SSR（卡牌抽卡语） | **常驻 / 人气 / 当期 / 图腾**（中文，去抽卡味） |
| 语义 | "稀有" | **"本次抽取的话题度"**——按官方标签与价格分位自动判定 |
| 是否影响价格 | 否 | 否（且必须在卡片上写明） |
| 是否代表性发行量 | 未声明 | **必须显式声明"不代表官方发行量、限量或稀缺性"** |

`experience.rarityNote` 固定文案（不可省略、不可改写）：
> 「分级是本项目玩法设定，仅影响卡面视觉与文案，不代表官方发行量、限量或稀缺性。」

---

## D4 · 系列命名：全部原创，且显式否定官方属性

A 的系列名（牛堡宇宙/脆鸡江湖）本身已是原创中文命名，符合 B 要求。补充两条：

1. 所有系列名**不得**与麦当劳官方产品名、活动名相同（如不得叫"随心配盲盒""1+1 盲盒"）。
2. 首次展示系列时追加一行：`系列为本项目原创体验主题，非麦当劳官方系列。`

落地：`series.json` 每个系列带 `disclaimer` 字段，由 SKILL.md 强制输出。

## D5 · 视觉：不做"包装图"，做"收藏卡"

### D5.0 先澄清一个常见误解：官方食物图是拿得到的

`query-meals` 返回的每一项都带 `image` 字段，指向麦当劳官方 CDN：

```
https://menu-img.mcd.cn/pcm/prod/menu/20260309/product/MS_1100_320.png   # 巨无霸
```

所以**食物照片本身不需要画、不需要生成**，直接嵌进卡片即可（`<image href="…">`）。
`query-meal-detail` 还会返回 `_600.png` 的大图，需要高清卡面时用它。

**那 SVG 画的是什么？** 画的是食物照片**外面那一层**：

| 层 | 内容 | 为什么必须自研 |
|---|---|---|
| 食物照片 | 官方 CDN 图 | — 直接引用，不加工 |
| 系列色背景 / 条纹纹理 | SVG 渐变 + pattern | 官方没有"盲盒"这个物料，不存在可引用的设计稿 |
| 稀有度边框 / 光效 | SVG 渐变 + blur | 同上；且必须可按等级切换 |
| 编号 / 价格 / 属性 / 水印 | SVG 文本 | 本项目玩法数据，官方没有 |
| 盒面概念插画（可选，P1） | 原创 | 若制作，必须标「概念设计，非官方商品包装」 |

**三个理由，缺一不可**：

1. **没有东西可引用**。官方给的是白底商品抠图，不是盲盒包装。要做"开盒"，就必须自己造"盒面"，否则那只是菜单。
2. **不能伪造**。把官方 Logo / 金拱门 / 包装设计稿拼上去 = 侵权 + 误导（D5 正文）。自研外壳是唯一安全解。
3. **必须可批量、可复现、可改色**。一次开盒要在 1 秒内出图，且同一张卡每次渲染必须一致（对应 `seedHash` 可验真）。模板化 SVG 满足全部三条；AI 生图既不保证一致性，也慢。

> **降级路径**：客户端不支持渲染图片时，SKILL.md 要求退化为"文本卡 + 官方图片的 Markdown 链接"，功能不受影响。渲染能力**不是**功能可用的前提。

### D5.1 边界细则

| 元素 | 来源 | 边界 |
|---|---|---|
| 商品实拍图 | MCP `image` 字段（官方 CDN） | 属官方数据，可直接用；**不得**二次加工成"官方包装样式" |
| 卡框 / 系列色 / 光效 / 编号 | 本项目程序化 SVG | 原创，无外链素材 |
| 麦当劳 Logo / 金拱门图形 / "i'm lovin' it" | **禁止使用** | — |
| 概念封面（若制作） | 本项目原创 | 标注「概念设计，非官方商品包装」 |
| 卡面水印 | 固定 | 「非官方产品 · 参赛作品」 |

## D6 · 收藏：本地持久化，但不是"账户体系"

B 主张会话内，A 主张图鉴（需要跨会话）。

**裁决：本地 JSON 文件，无账号、无云端、可一键清除。**

- 路径 `~/.popmc/collection.json`，只存 `productCode` + 时间 + 计数。
- 不存：手机号、地址、Token、门店地址（只存 storeCode）。
- 卡片与图鉴页必须写明：「收藏记录是抽取历史，不代表购买记录，也不代表该商品当前仍在售。」
- 用户说"清除我的收藏"→ 直接删文件，不做挽留。

---

## D7 · 随机算法：确定性种子 + 概率公示 + 保底（采纳 A，保留 B 的无保底模式）

B 的 MVP 是"均匀随机"，简单但三个问题：不可复现（无法审计）、无概率公示（盲盒合规要求）、无保底（体验差）。

**裁决：以 A 的确定性引擎为默认，但暴露 `--fair` 开关给"纯随缘"模式。**

| 模式 | 行为 | 用途 |
|---|---|---|
| `default` | 等级加权 + 保底 + 种子可复现 | 主玩法 |
| `fair` | 候选集合内均匀随机，无等级 | 用户说"别搞花样，就随机一个" |

无论哪种模式，**候选集合都经过同一套硬约束过滤**（预算/排除/可售）。

---

## D8 · 情绪映射：新增为独立规则层（采纳 B）

A 缺这块，而它正是"情绪价值"的落点。B 的 `moodTags` 方向正确，但没给规则。

**裁决：新增 `data/moods.json`，情绪 → (系列权重, 口味倾向, 文案语气)。**

情绪不直接改商品，只改**候选系列的选择概率**与**文案语气**——这样既影响结果，又不破坏"事实层不受创意层污染"的原则。

## D9 · MCP 工具集：6 个，全部以 Schema 为准

采纳 B 的清单，并补充 A 的实测踩坑作为前置约束。

| Tool | 用途 | 频次 | 备注 |
|---|---|---|---|
| `now-time-info` | 时段判定（早餐/午/下午茶/夜宵） | 1/次 | 系列可用性依赖它 |
| `query-nearby-stores` | 定位门店 | 1/次 | 到店 `beType=1` 无 beCode |
| `query-meals` | **建池唯一来源** | 1/次（缓存 10min） | 分类名含 `\n`，需归一化 |
| `list-nutrition-foods` | 卡面属性 + "能量约…"原话 | 1/进程 | 返回是字符串，需自解析 |
| `query-meal-detail` | 套餐组成（用户点开详情时） | 按需 | 有套餐才有意义 |
| `calculate-price` | 只读算价 | 门 1 | 单位是**分** |
| `create-order` | 下单 | 门 2 | 需 `takeWayCode` |
| `campaign-calendar` | 活动 → 文案灵感/主题 | **P2，不用于事实** | 活动商品未必在售，禁止当商品源 |

**明确禁止**：把活动日历里的商品当作候选池来源。活动 ≠ 在售。

## 附：空候选池协议（对应 B 的"不得虚构结果"）

候选池为空时，**禁止**降级为"随便给一个"，必须返回结构化说明：

```json
{ "ok": false, "reason": "budget_too_low", "detail": "该店当前最便宜的餐品是 ¥5 圆筒冰淇淋，¥3 预算内无可用选项。",
  "relax": [{ "action": "raise_budget", "to": 5 }, { "action": "switch_series", "to": "dessert" }] }
```

`reason` 枚举：`no_store` / `store_closed` / `empty_menu` / `budget_too_low` / `all_excluded` / `series_unavailable` / `auth_failed` / `rate_limited`

> 这条是"事实优先于体验"的最后一道闸门。宁可承认没得抽，也不能编一个。

## D11 · v1.1 引擎补丁（实现期发现的五个真问题）

以下五条不是新设计，是**原设计在执行时会出错**的地方，按同一套原则修掉。

### D11.1 时段闸门：早餐不能在半夜被抽出来

`series.json` 早就有 `availableHours`，但代码从未读取——18:39 抽盒会正常输出「晨光早餐」，
用户拿到的是一份 10:30 就停售的建议。这是"事实与体验不一致"的最典型形态。

**裁决：把 `availableWindow` 做成硬闸门**，与预算同级：不在时段内直接返回 `series_unavailable`，
附当前可用系列。字段升级为 `["05:00","10:30"]`（支持跨零点），旧 `availableHours` 兼容。

> 这条同时是"降低对 MCP 依赖"的收益：时段是本地可算的事实，不该等 `now-time-info` 才能判断。

### D11.2 空池三态：不能把"没上市"说成"你太穷"

原实现只区分 `all_excluded` / `budget_too_low`。当某系列在本店一个商品都没有时，
它会报"预算 ¥0 抽不出来，可选：无"——把系统的空池说成用户的问题，是误导。

**裁决：按 `raw → afterExcl → cand` 三段分别判定**，产生 `series_unavailable` / `all_excluded` / `budget_too_low`。

### D11.3 nonce 自增 + 近期去重：`再抽一次` 必须真的变

两处叠加导致体验崩坏：
1. `nonce` 靠调用方手动传，LLM 一忘，同一天必然拿到同一张卡（种子一模一样的确定性）；
2. 即使 nonce 变了，等级加权下 N 档卡少，实测 5 连抽里出现 3 次同款鸡翅。

**裁决：**
- `nonce` 由 `state.counters.dailyNonce[day]` 自增，不再要求调用方维护；
- `state.recent` 记住最近 4 个 `productCode`，抽卡时先避开；
  若该等级已全是抽过的，退到**整池**未抽过的卡——**宁可变档，也不重复**；整池都抽过才允许重复。

> 与 D7 不冲突：种子仍然确定，只是"避开清单"也进了种子材料，所以复现依旧成立。

### D11.4 营养匹配：`可乐` 对不上 `可乐中杯`

纯精确匹配让饮品覆盖率只有 4/13、小食 2/13。菜单名和营养表名的粒度本来就不同。

**裁决：只接受"唯一 + 后缀只是规格/包装"的映射**，其余仍拒绝。`可乐→可乐中杯` 通过，
`麦乐鸡→麦乐鸡4块/5块`（多候选）、`薯条→中薯条/大薯条`（多候选）、`麦辣鸡腿堡→…三件套`（不同商品）全部拒绝。

匹配成功必须在卡面写明 `营养按官方营养表「可乐中杯」条目`，并写入 `fact.nutritionMatch`。
**判据是可核对性，不是相似度**——这是 D1"fact 不补齐"的延伸，不是例外。

### D11.5 端盒：预算只做减法，不做"优惠"

端盒（主食+小食+饮料）是"抽完就能吃一顿"的落点，原 SPEC 只有伪代码。落地时明确两条：

1. **总价永远是单品现价累加**，不引入任何"套餐套路价"或自造折扣——打折是官方的事。
2. **永远不超预算**：先给主食预留"最便宜小食+最便宜饮料"，装不下就降级结构（3→2→1 件）并写进 warnings。

> 端盒的小食/饮料不得继承主食系列的文案钩子（否则一杯清水会被写成"咔嚓一声"）。

### D11.6 商品图必须内联成 data URI（不然交付物是"裂图"）

**现象**：卡面用 `<image href="https://menu-img.mcd.cn/...">` 引用官方图，本地用浏览器直接打开 SVG 时正常；
但一旦被 `<img src="../assets/cards/chicken-SR.svg">` 引用（GitHub README、HTML 预览页都是这么干的），**食物图全部裂掉**——
浏览器出于安全策略，禁止 SVG-in-`<img>` 加载任何外部资源。

这属于"功能没坏但交付物看起来是坏的"，比崩溃更伤：评审第一眼看到的就是一排裂图。

**裁决：渲染时把官方商品图下载并内联成 `data:image/...;base64,`，默认开启。**

- 缓存到 `~/.popmc/imgcache/`（按 URL 的 sha1），二次渲染 <10ms。
- 下载失败（离线/超时）**不中断抽盒**，回落到原始 URL 并打一行 stderr 警告。
- `--no-embed` 可关掉，用于需要"只引用、不复制"的场景。
- 图片本身仍是官方 CDN 原图，**未做任何加工**，只是换了传输方式，不违反 D5.1 的边界。

代价：单张卡 SVG 从 ~6KB 变成 ~50-100KB（12 张约 1.1MB）。为了 README 第一屏能看，值得。

## D12 · 逻辑设计深度优化（约束感知调度与智能自愈）

### D12.1 约束感知系列调度（Constraint-Aware Series Routing）
- **痛点**：原逻辑先凭情绪加权选系列，再过滤预算。若挑中高价系列（如牛堡宇宙），即使用户没指定系列且全店有低价美食（如 ¥5 圆筒），也会误报 `budget_too_low`。
- **裁决**：未指定系列时，调度器**先探测各系列在硬约束下的有效候选数**，只在有货可出的系列中执行情绪抽样；彻底消除误报空池。

### D12.2 防疲劳多样性平衡（Anti-Fatigue Diversity）
- 检查 `state.recent`，若检测到最近连续 2 次抽中同类品类（如连中两次套餐），自动将其他品类的抽样权重上调 1.5 倍，确保像真实潮玩盲盒一样保持探索新鲜感。

### D12.3 极低预算自愈与最小差额诊断（Budget Auto-Healing Delta）
- 当全店均无法满足用户极端过低预算（如 ¥3）时，系统自动探测全店最低门槛美食（如 ¥5.0 圆筒），并在 `relax` 中输出精确最小差额：`仅差 ¥2 即可解锁【圆筒冰淇淋】`，避免死板冰冷拒绝。
